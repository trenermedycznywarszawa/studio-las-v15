# 05 Report System

## Purpose

This document defines the Studio Las report system.

A report is not a PDF.

A report is not a summary of completed workouts.

A report is not a decorative client document.

A Studio Las report is a decision point.

It turns the process into understanding and the understanding into the next decision.

## Core principle

The report should answer:

> What did we discover and what should happen next?

It should not merely answer:

> How many sessions happened?

The report exists to show the pattern.

Core rule:

> Paper guides the morning.  
> Trainer gives meaning.  
> App records the signal.  
> Report shows the pattern.

This is a design heuristic, not a required interface sequence. Report meaning still requires trainer review regardless of whether guidance was delivered on paper, in the app, or through a deliberate hybrid.

## Report doctrine

The report is trainer-led interpretation.

It should combine:

- the client's starting context,
- trainer hypotheses,
- session observations,
- home guidance signals,
- selected measurements,
- visible changes,
- unresolved limitations,
- the next decision.

The report should reduce confusion.

It should not overwhelm the client with raw data.

## What a report is

A Studio Las report is:

- a mirror of the process,
- a record of what changed,
- a structured interpretation,
- a decision support document,
- a bridge between one process cycle and the next,
- a client education moment,
- a way to build long-term continuity.

## What a report is not

A Studio Las report is not:

- a workout attendance certificate,
- a leaderboard,
- a scorecard,
- a medical diagnosis,
- a generic progress PDF,
- a dashboard export,
- a marketing document disguised as care,
- an automatic AI verdict,
- a list of all available data.

## Report questions

Every report should answer the following questions:

1. Where did the client start?
2. What were the initial hypotheses?
3. What did we do?
4. What signals did we observe?
5. What changed?
6. What did not change?
7. What surprised us?
8. What is now safer or easier?
9. What still requires attention?
10. What should the client do next?
11. What should the trainer do next?
12. Should the process continue, change, reduce, pause, or end?

## Report timing

Reports may exist at different levels:

### 4-week review

A short early review.

Purpose:

- check whether the direction is working,
- identify early barriers,
- adjust hypotheses,
- prevent drifting.

### 8-week review

A mid-process review.

Purpose:

- confirm patterns,
- refine the plan,
- prepare the client for greater independence,
- decide whether the final 12-week focus should change.

### 12-week report

The main process report.

Purpose:

- summarize the full cycle,
- show meaningful changes,
- identify remaining limitations,
- define the next decision.

The 12-week report should be treated as a major Studio Las product artifact.

## Report structure

A strong Studio Las report may include:

1. Client starting point  
   The situation at entry.

2. Main goals or desired recovery  
   What the client wanted to regain.

3. Initial hypotheses  
   What the trainer believed might be limiting progress.

4. Process summary  
   What was done, in human language.

5. Key observations  
   What the trainer noticed across time.

6. Selected measurements  
   Only the measurements that clarify progress or decision.

7. Functional changes  
   What the client can now do, tolerate, or understand better.

8. Client signals  
   What the client reported or demonstrated.

9. Pattern interpretation  
   What the process revealed.

10. Remaining risks or limits  
    What still needs caution.

11. Next decision  
    Continue, change focus, reduce support, refer, pause, or finish.

12. Trainer note  
    A short personal interpretation from the trainer.

## Pattern over volume

A report should show patterns, not volume.

Weak report logic:

- 12 sessions completed,
- 8 home tasks completed,
- weight changed by X,
- RPE averaged Y.

Strong report logic:

- fear decreased in loaded knee flexion,
- home consistency improved after the protocol was simplified,
- pain response remained stable under gradual load,
- confidence improved before objective capacity fully changed,
- the next limitation is recovery, not exercise selection.

Volume may support the report.

Volume is not the report.

## Client-facing language

The report should use calm, clear language.

It should avoid:

- medical claims beyond scope,
- shame,
- exaggerated transformation language,
- complex jargon,
- over-certainty,
- raw data overload.

The client should finish the report with:

- more clarity,
- more trust,
- a better sense of what changed,
- a concrete next step.

## Trainer-facing value

The report also helps the trainer.

It should preserve learning:

- which hypotheses were useful,
- which interventions worked,
- which signals mattered,
- where the process changed,
- what should be repeated with similar clients,
- what should not be assumed next time.

Over years, reports can become Studio Las internal evidence.

## Report and AI

AI may support the trainer by organizing notes, surfacing candidate patterns, or drafting report sections.

AI must not become the source of authority.

The trainer owns interpretation and final decision.

The client should not receive an unreviewed AI verdict.

## Report and Studio Las OS

Studio Las OS should support reports by preserving report-ready signals.

It should not force the trainer to collect unnecessary data just to fill a template.

The report system should drive what data matters.

The database should not decide what the report means.

## Report success criteria

A report is successful when it:

- explains the process clearly,
- shows meaningful patterns,
- connects evidence to interpretation,
- supports the next decision,
- respects the client's dignity,
- strengthens trust in the body,
- helps the trainer continue or close the process responsibly.

A report fails when it:

- lists data without meaning,
- celebrates attendance instead of change,
- creates pressure or shame,
- hides uncertainty,
- gives medical certainty outside scope,
- becomes a dashboard export.

## Implication for future work

Before building any report feature, define:

1. What decision should the report support?
2. What pattern should it reveal?
3. What minimum signals are required?
4. What should stay trainer-only?
5. What should the client actually see?
6. What must not be automated?

The report is a decision artifact first.

PDF generation is only an implementation detail.
