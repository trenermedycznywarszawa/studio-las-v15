# ADR 20 — Stage 2 Production Implementation Direction

**Status:** OWNER ACCEPTED — IMPLEMENTATION DIRECTION APPROVED
**Accepted:** 2026-09-01
**Scope:** Stage 2 first inquiry → human call → trainer decision → explicit conversion into the existing client/PWD architecture
**Base contract:** `docs/architecture/19_STAGE_2_PRODUCTION_RUNTIME_CONTRACT.md`
**Implementation gate:** staging-only first; production cutover requires separate verification

## Decision

Studio Las will implement the smallest production-safe pre-client boundary needed to preserve first-contact context and trainer decisions without introducing a CRM or a second client identity model.

Approved physical direction:

`public form → inquiry → trainer call → inquiry decision history → explicit conversion → existing clients/PWD`

Approved new persistent concepts:

1. `inquiries`
2. `inquiry_decisions`

Not approved:

- `people` table;
- `service_episodes` table;
- sales pipeline/funnel;
- lead scoring;
- conversion analytics dashboard;
- marketing automation;
- automatic qualification;
- automatic client creation;
- AI runtime/provider in this slice.

`Person → Inquiry → Service Relationship` remains the domain model, not the physical schema.

## Why this is the minimum justified schema

The existing `clients` root already owns the secure Studio Las process after a person enters PWD/client workflow. Reusing `clients` for public inquiries would make an interested person indistinguishable from a person already in the Studio Las process and would contaminate client lifecycle, access, intake, PWD and reporting semantics.

A single mutable inquiry record is also insufficient because trainer decisions can legitimately change, for example:

`FOLLOW_UP → PWD`

Decision history therefore needs append-only/versioned persistence separate from the current inquiry operational state.

## Inquiry boundary

`inquiries` represents one first-contact episode before conversion.

Minimum responsibilities:

- stable opaque ID;
- owner trainer;
- source/version metadata;
- submitted name;
- submitted phone;
- optional submitted email;
- preferred contact window;
- submitted broad goal category;
- optional short person-authored sentence;
- privacy/notice version;
- inquiry status: `open | converted | closed`;
- contact status: `pending | contacting | completed | unreachable`;
- next action type/time only when operationally needed;
- closure/conversion metadata;
- nullable `converted_client_id` only after successful explicit conversion;
- retention/deletion metadata as required by the later privacy decision.

### Explicitly rejected field

Do **not** persist or reintroduce a travel/commute-area field in Stage 2 v1.

The current owner-approved public form deliberately removed that question because it does not improve the first-contact decision enough to justify the space or data. Any earlier candidate wording in Contract 19 referring to an optional travel-area category is superseded by this ADR.

## Inquiry decision boundary

`inquiry_decisions` is append-only/versioned trainer-owned decision history.

Minimum responsibilities:

- decision ID;
- inquiry ID;
- explicit decision value;
- goal in the person's own words;
- optional `why_now` only when decision-relevant;
- short current barrier/context;
- short rationale;
- optional referral/boundary note;
- next action type/time when relevant;
- actor/time;
- supersedes relation or equivalent active/superseded semantics;
- evidence/source-version references sufficient to preserve truthful provenance.

Allowed trainer decisions:

- `PWD`;
- `FOLLOW_UP`;
- `NOT_NOW`;
- `REFERRED`;
- `NOT_A_FIT`;
- `CLOSED_BY_PERSON`.

`unreachable` is a contact status, never a trainer decision.

No decision may be preselected, inferred from form fields, generated by AI, or saved without an explicit trainer action and rationale.

## PWD recommendation vs conversion

`PWD` means the trainer believes PWD is the appropriate next step. It does not create a client.

Before agreement:

- inquiry remains `open`;
- no client row;
- no PWD row;
- no full intake automatically sent;
- next action may be `arrange_pwd`.

Only after PWD is explicitly agreed may the trainer invoke a deliberate conversion action such as:

`Utwórz klienta do PWD`

Conversion must be atomic.

Successful conversion must:

1. verify authenticated owner trainer and required AAL;
2. validate current inquiry and active decision/context;
3. create exactly one existing `clients` record from allowlisted confirmed identity/contact fields only;
4. set `converted_client_id`;
5. mark inquiry `converted`;
6. preserve inquiry and decision history;
7. return the new client ID for the existing secure pre-PWD/PWD workflow.

It must not:

- copy complete call notes into `clients`;
- populate health/PWD fields from inquiry free text;
- create Home Guidance;
- invite a client account;
- publish anything client-facing;
- create diagnosis, plan or AI interpretation.

## Public ingress decision

The owner-approved target architecture is a bounded Studio Las/Supabase public-write ingress.

Formspree remains a temporary transport/fallback during the transition. It is not the long-term source of truth.

### Staging-first transition

The first implementation slice must **not** switch the public production form.

Order:

1. implement schema/security/trainer workflow on staging;
2. implement and test a bounded staging public ingress using synthetic data;
3. run automated E2E including abuse/invalid-payload/failure cases;
4. verify no regression to current public Formspree path;
5. only after a separate owner-approved cutover task change the public form transport;
6. retain a deliberate fallback/rollback path during cutover.

### Public ingress requirements

The direct ingress must provide at minimum:

- strict allowlist schema;
- field length/type validation;
- exact public-form/source version;
- payload size limits;
- spam/rate-abuse control appropriate for the threat model;
- no public read surface;
- no anonymous read/update/delete;
- no service-role secret in browser code;
- no anonymous writes to `clients`, `inquiry_decisions`, PWD or other process tables;
- observable errors and no false-success UI;
- safe handling of duplicate/retry submissions;
- no AI invocation;
- no logging of contact/free-text content in ordinary technical logs.

## Trainer runtime

The v1 trainer surface is not a CRM.

It should show only:

- person/contact request;
- preferred contact window;
- broad selected goal;
- optional own words;
- deterministic Call Brief;
- contact state;
- after-call decision memo;
- explicit next action.

After-call UI order:

1. `Co ta osoba chce realnie odzyskać?`
2. optional `Dlaczego jest to ważne teraz?`
3. `Co dziś najbardziej utrudnia kolejny krok?`
4. explicit decision;
5. decision-specific field only when needed;
6. short rationale;
7. next action/time only when relevant;
8. explicit save.

No funnel, lead score, conversion probability, nurturing queue, sales KPI or urgency mechanic.

## Security and audit

The implementation must inherit the existing Studio Las OS security model rather than create a parallel one.

Trainer-side writes/decision/conversion must use the established patterns where applicable:

- authenticated trainer;
- owner scoping;
- AAL2 for sensitive mutations;
- RLS/least privilege;
- SECURITY DEFINER RPCs only where justified, with fixed `search_path`;
- explicit grants/revokes;
- no direct protected-table browser writes where an atomic validated RPC is required;
- cross-inquiry/client isolation tests;
- metadata-only audit.

Audit must not duplicate phone, email, inquiry text, call notes, rationale or health content.

## Privacy and retention gate

This ADR approves the staging implementation direction, not production processing of the new direct ingress.

Before production cutover, a separate decision must define:

- privacy notice wording/version for direct Studio Las storage;
- lawful basis and handling of voluntarily submitted sensitive information;
- non-converted inquiry retention period;
- converted inquiry provenance retention;
- spam/test deletion behavior;
- anonymization/deletion semantics;
- Formspree transition/removal implications.

Do not retain non-converted inquiries indefinitely by default.

## Implementation slice authorized by this ADR

A Codex implementation task may now prepare a Draft PR against `product-recovery` for a **staging-only** Stage 2 runtime slice containing only what is necessary to prove the architecture.

Expected slice:

- migrations for `inquiries` and `inquiry_decisions`;
- RLS/privilege/audit coverage;
- validated trainer mutation RPCs;
- atomic inquiry → existing client conversion RPC;
- trainer-only inquiry/after-call UI integrated into the existing Studio Las OS architecture;
- deterministic Call Brief reuse;
- staging-only bounded public ingress or a clearly isolated staging fixture path, depending on repository/runtime constraints found during implementation;
- automated SQL/security/browser E2E;
- synthetic data only for staging verification;
- cleanup of synthetic records after tests.

## Explicitly forbidden in the first implementation PR

Do not change:

- production public form transport;
- `main` deployment;
- existing PWD semantics or `save_pwd_workflow` behavior;
- Guidance Release/Home Guidance behavior;
- client portal/client-safe projections;
- existing client account lifecycle;
- AI provider/runtime;
- email/SMS sending;
- booking system;
- analytics dashboards;
- existing client health/process schema except the minimal foreign-key/integration point strictly required for atomic conversion.

Do not introduce:

- `people`;
- `service_episodes`;
- generic CRM tables;
- lead scoring;
- marketing automation;
- health fields on the public inquiry path;
- persistent full-call transcript.

## Acceptance criteria for the implementation PR

The implementation is not ready for owner merge decision unless automated evidence demonstrates at least:

1. one valid synthetic inquiry can be created through the approved staging path;
2. invalid/oversized/unknown fields are rejected without mutation;
3. anonymous/public actor cannot read inquiries;
4. anonymous/public actor cannot create decisions, clients or mutate inquiries after creation;
5. trainer A cannot access trainer B inquiry data;
6. decision cannot save without an explicit allowed value and non-empty rationale;
7. `unreachable` cannot be stored as a decision;
8. a second decision supersedes rather than overwrites the first;
9. `PWD` decision alone creates no `clients` row;
10. atomic conversion creates exactly one client and marks exactly one inquiry converted;
11. failed conversion leaves no partial client/inquiry state;
12. repeated conversion is blocked/idempotent according to the implemented contract;
13. conversion copies only allowlisted identity/contact fields;
14. no Guidance, PWD result, client account or client-facing publication is created by conversion;
15. metadata audit contains no contact/free-text/rationale content;
16. browser performs no forbidden direct writes to protected tables;
17. existing PWD and Guidance automated regression tests continue to pass;
18. mobile 360×900 and keyboard smoke pass for the trainer surface;
19. synthetic staging data is removed after verification;
20. no production migration/app/public-form change is executed during verification.

## Required Codex final report

Codex must finish with a concise report containing:

- branch and PR;
- exact HEAD SHA and tree SHA;
- changed files and migrations;
- final physical schema and why each field exists;
- RPCs and privileges/RLS summary;
- ingress implementation used on staging;
- test commands and exact results;
- staging project/ref used;
- synthetic data created and cleanup result;
- explicit production-read-only/no-production-change statement;
- explicit `main` untouched statement;
- PWD/Guidance/client-access regression result;
- known residual risks/open decisions;
- verdict: `READY FOR INDEPENDENT AUDIT` or `NOT READY`.

Codex must not merge the PR or mark it ready for owner merge on its own.

## Supersession / clarification

This ADR is normative for the two owner decisions made on 2026-09-01:

1. minimal new physical schema (`inquiries` + `inquiry_decisions`) is approved for the staging implementation slice;
2. bounded direct Studio Las/Supabase ingress is the target transport, with Formspree retained temporarily until separate verified cutover.

Where Contract 19 still presents the ingress choice as open or mentions an optional travel-area field, this ADR controls until Contract 19 is normalized in a later documentation cleanup.
